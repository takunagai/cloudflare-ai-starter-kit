## 3つの推奨設定

「プリセット」は、既存設定の組み合わせと導入手順をまとめた推奨設定を指す。新しい認証方式や汎用プラグイン基盤は追加しない。

| 用途 | 開始方法・認証 | AI・追加接続 | 完成時に提供するもの |
| --- | --- | --- | --- |
| 1. ローカル試作 | 既存のローカルBetter Auth、架空アカウント、ローカルD1 | 固定応答、実メールなし、任意拡張OFF | 外部アカウント・実Secretなしでチャットと履歴を試す導入手順 |
| 2. 個人・社内利用 | Cloudflare Accessとアプリの所有権確認 | 選択したproviderだけ。Accessの本人認証に必要な通知等は別に扱う | 保護範囲・利用者・セッション・モデル・予算を明示した設定例と検証手順 |
| 3. 公開サービス | Better Authの登録・ログイン・メール確認・再設定 | 実メールと選択したprovider。Googleや決済は必要時のみ | 公開ページと保護APIを区別し、認証・利用制限・復旧まで確認する導入手順 |

2・3向けを選んでも、開発初期は共通のローカル固定応答で確認できる。ローカル確認で使う認証と、配備先で採用する認証を明記し、ローカルの省略設定をクラウドへ持ち込まない。未選択のprovider・任意拡張にアカウントやSecretを要求しない。

### 判定順と台帳の扱い

1. 既存の環境/origin境界を確認する。新ポリシーの列挙値・矛盾は専用関数で判定するが、AI設定の不備を認証・ログアウト・既存履歴の閲覧/削除を止める理由にしない。生成・拡張の対象入口で固定コードの503として扱い、値・資格情報・個別URLを応答やログへ出さない。
2. `verification`なら現行制御へ渡す。省略・enabled=false・AI bindingなし・期限切れは、従来どおり実AI不可。総3回・単一所有者・失敗消費・固定窓は変更しない。
3. `standard`なら認証後、D1の旧`ai_verification`行の**存在だけ**を確認する。行あり・照会失敗・0006未適用ならモデル利用不可とし、生成・拡張の受付/実行/関連更新を503で拒否する。既存履歴の閲覧/削除やログアウトは通常の認可で継続できる。行の内容取得・削除・更新は不要。新環境ではテーブルあり/行なしで通常経路を使う。別DBへ既存台帳をコピーしない。
4. 認証・所有権・利用制限、モデル選択、資格情報/binding充足を通って初めて外部処理へ進む。チャット予約と実行、RAG/画像/決済入口、Workflow受付と各外部処理stepで同じ方針を確認する。予約後の設定不適合・失敗は既存の消費/失敗記録を保持する。
5. `/api/ai-verification`は認証必須・GETのみ・no-storeを維持。通常経路では既存応答形の`ready:false, remaining:0`を返し、「通常AIがOFF」や「通常枠ゼロ」の意味に使わない。モデル一覧は通常の選択と充足で判定する。

台帳照会の追加先はHTTP APIだけでなく、バックグラウンド実行も含む。拡張OFFの404、認証不成立の401、所有権拒否とポリシー503の優先順をテストで固定し、未認証に台帳状態を知らせない。DBの存在検査は初版では通常stagingの認証済み実行入口で行い、永続的な「行なし」cacheはしない。

同期的な設定判定と非同期のD1確認は分ける。現行`listModels/getModel`へDB読み取りを隠して追加せず、認証済み一覧APIで台帳を含む利用可否を合成し、チャット/各拡張の実行直前にも同じ非同期guardを通す。署名で認証するwebhookは利用者sessionを要求せず、署名検証後・DB更新前にこのguardを適用する。Workflowは永続jobの所有者/状態を確認してから外部処理へ進む。

| 入口 | 拒否・継続の優先順（新しい通常経路） |
| --- | --- |
| 公開ページ・認証・session・会話のCRUD | 既存の環境/origin・認証・所有権・method/input検証を維持。AI OFFやモデル設定不備だけでは遮断しない。新ポリシー無効時のsessionの拡張表示は全OFF |
| モデル一覧 | 環境/origin → 認証 → method。ポリシー/台帳不適合は既存catalogの全件`available:false`、推論0。値を含まない説明は導入文書で補う |
| チャット生成 | 環境/origin → 認証 → method/body/所有権 → ポリシー/台帳 → モデル/拡張選択 → 原子的な利用枠予約 → 実行直前再確認。拒否により別モデルへ進まない |
| 任意拡張API | 現行のOFF時404を維持。ON時は認証・method/input・所有権 → ポリシー/台帳 → 必須設定 → 外部処理。AI_MODE単独では独立拡張を遮断しない |
| 決済webhook | 拡張OFFなら404。ONならmethod/body上限/署名 → ポリシー/台帳 → 冪等なDB更新。不適合を2xxで受領済みにせず、再送が必要な503として扱う |
| Workflow再開 | 永続job/所有者/状態 → ポリシー/台帳/選択モデル → 外部処理step。再開時にも確認し、拒否時に生成を開始しない |

これは新しい通常経路の契約であり、旧検証経路の既存エラーコード・消費規則をまとめて変えるものではない。台帳確認と別リクエストの書込みを一つのtransactionにできると仮定せず、新しい通常環境へ旧検証Workerを接続しない運用分離を前提とする。guardの存在だけで共有DBの同時利用を安全としない。

DB管理者が設定/DBを置き換える操作までアプリ内で封じる案ではない。工程E前に新しいWorker・DB・build成果物が旧検証先と分離していることを、実値を記録せず本人照合する。旧DBを通常へ転換するmigrationや台帳リセットは初版対象外。既存0001〜0006の編集、新migrationは本案では不要。

### 通常stagingで維持する上限と費用境界

通常経路は[チャットの標準上限](chat.md)を維持する。利用者ごと60要求/UTC日・同時1件・10要求/分、入力8,000文字/body 40,000 bytes、履歴20件/16,000文字、出力1,024 tokens/step、timeout 60秒、retry 0。拡張OFFならモデルstep 1、agentを別途ONにした場合のみ既存最大3stepを使う。これらは検証専用の総3回/30分とは異なり、利用者全体の総額を止める機構ではない。

## 標準基盤: TypeSafe AI Jev（2026-10-02）

本人の明示指示により、Jevを共通スターターの標準判断基盤として採用する。先の「B〜D後の任意拡張」という推奨はこの指示で変更した。[公式調査と標準搭載範囲](../references/typesafe-jev-20261002.md)を根拠とし、全3用途に同じ判断service・テスト・利用例・手順を含める。RAGやagentの有効化を前提にせず、拡張フラグ`ENABLE_*`にも分類しない。

Jevは文章生成ではなく、選択・採点・真偽の確率を返すため、チャットモデルの一覧・AI_ALLOWED_MODELSへ追加せず、専用の型付き判断serviceから利用する。共通基盤への搭載と外部APIへの接続は区別する。標準起動/CIはAPIキーなしで動き、実接続は以下の明示設定後だけ。チャットごとの自動呼出しや認可判断の委譲は追加しない。

| 設定・境界 | 標準基盤としての設計契約 |
| --- | --- |
| `JEV_MODE` | `off` / `remote`。全用途の既定値はoff、省略もoff。空・未知値を拒否。offは判断要求を未接続として返し、実推論や推測結果で代替しない |
| `JEV_MODEL` | remote時に必須。B-1で公式再確認した固定版`jev-1.13.0`のみ許可。latest/previewの自動追従、クライアントからの自由指定はしない。off時は省略（空文字も拒否）。提供継続と実利用可否はE前に再確認 |
| `TYPESAFE_API_KEY` | remote時だけ必要なサーバー側Secret。設定があっても自動接続しない。人間が別ターミナルで投入し、エージェントは値を扱わない |
| チャットとの関係 | AI_MODEとJEV_MODEは独立。チャットOFF＋Jev接続、チャット接続＋Jev OFFを許容。両方を止める場合は各設定をOFFにする |
| 旧検証staging | モード省略/verificationではJev実行を必ず拒否し、既存の検証台帳・消費・終了状態を維持。標準搭載を過去の接続許可へ読み替えない |
| ローカル検証 | 外部境界は合成fixture/fake HTTP。実Jevの判断や日本語精度の証拠にしない。実接続不可時のチャット機能維持も検証 |
| 実行境界 | 認証/所有権・原子的な受付枠・要求ID重複防止・入力/質問数上限・timeout・retry 0。認可や副作用の承認はコード/人間が担う |

## 重要な設計・検証項目

- 共通の利用者識別と所有権確認を維持する。AccessからBetter Authへ変更する場合は、利用者ID・会話等の所有者・セッションの移行を別に設計する。同じメールを理由に自動統合しない。
- 既存stagingは固定窓・指定FP8・総3回の検証専用。通常stagingはB-1〜B-4で実装/ローカル検証済みだが、別Worker/DBの実設定・実配備は未実施。検証フラグOFF、台帳削除、開始日時変更で解除する方法は採らない。
- AI接続は用途と独立して選ぶ。モデル許可、入力/出力上限、再試行、利用枠、費用確認を定義する。回数制限を硬い請求上限と説明しない。
- 任意拡張は全OFFを基準に、最初の用途で必要なものだけ追加する。全provider・全拡張の実接続を初版の必須条件にしない。
- 既存の認証・SQL・所有権検証を活かし、変更した境界と導入手順の不足に応じて検証する。ローカルで確認できる範囲と実Access・実メール・実AIで確認する範囲を分ける。
- local/staging/productionのDB、Secret、配備成果物を分離する。ローカルDB・アカウント・既存の配備設定を複製先へ流用しない。
