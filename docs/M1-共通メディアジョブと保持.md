## 設定と入口

| 設定・操作 | 動作と管理場所 |
| --- | --- |
| `ENABLE_MEDIA` | 省略/`"false"`は新規生成・モデル一覧を認証前404。`"true"`だけを有効候補とし、未知値も拒否する。公開wranglerと5プリセットはfalse |
| `MEDIA_ALLOWED_MODELS` | 12固定endpoint IDの重複なしJSON配列。有効時は空を拒否、OFF時は省略/`[]`。未知IDを転送しない。モデル別の[入力境界](../src/server/media/catalog.ts)と[設定判定](../src/server/media/policy.ts)を共有する |
| キー・素材binding | OFFはキー/R2不要。将来の実adapter実行時は明示許可モデルと`FAL_KEY`を検査する。M-1は実adapterを結線せず、有効/設定済みでも新規HTTP要求を`media_adapter_not_ready`で拒否する。キー投入やMEDIA_BUCKET追加を本書で要求しない |
| `ENABLE_IMAGES` | 旧FLUX経路だけを制御。新12件へ転送しない。新旧の枠は0008で合算し、旧APIの既存404や所有権を維持する |
| `AI_MODE` / `JEV_MODE` | メディアと独立。AI OFFをfal停止と扱わない。旧検証stagingは新旧メディアの外部呼出しを拒否し、既存台帳を変更しない |
| OFF・設定不備時の回復 | 本人のジョブ一覧/詳細・本文消去・取消意図の記録は認証後に使える。refreshの上流操作は有効化/許可モデル/キー/復旧gateが必要。旧検証stagingのメディア入口は404を維持 |

`GET /api/media/models`は許可したモデルだけを返し、全件にadapter未導入を表示する。`POST /api/media/jobs`は厳密なJSON（16 KiB、UTF-8、未知キー拒否）。`GET /api/media/jobs`は本人の直近50件と旧画像のmetadata、`GET /api/media/jobs/:id`は本人の保持中本文と出力素材ID、`DELETE`は本文の早期消去、`POST .../cancel`は取消意図、`POST .../refresh`は同一上流要求の確認/回収に限定する。全メディア応答はprivate/no-store。object key・provider URL・hash・キーをHTTPへ返さない。旧履歴は`legacy_external_url`/非private保存として表示し、過去URLを取得/コピーしない。

管理は公開用の[wrangler](../wrangler.jsonc)、[5設定例](../examples/presets/)、[service](../src/server/media/service.ts)、[ledger](../src/server/media/ledger.ts)で行う。実運用設定・Access保護・R2は今回未変更。ONへ変更する際はM-2以降のadapter/保存検証と、工程Eの対象・データ・費用・配備の別承認が必要。許可モデル追加は実利用権限やprivate出力の保証ではない。

## 原子的な予約と要求ID

新しい要求IDは`YYYY-MM-DD:UUIDv4`（UTC日付）を使う。新規IDは受付時のUTC日だけ許可し、保持中の同ID/同じ正規化入力は既存ジョブを返す。同ID/異入力は409。本文を消しても入力hash・利用量・時刻・状態の最小台帳を保持し、同じ要求を再送しない。保持後に同じ古い日付付きIDを使うと拒否する。UUID部が旧画像要求と衝突する場合も409。UUID部の同じ値に新しい日付を付けたものは別の要求IDであり、元IDの再利用ではない。

新ジョブ/本文/素材参照はD1 batchで登録し、INSERT triggerで利用枠・同時数・容量を原子的に確認して利用/容量を予約する。旧画像のINSERTも同じview/triggerを通す。0001〜0007や既存データは変更せず、[0008](../migrations/0008_media_jobs.sql)を追加した。旧Workerの通常SQLも追加表を無視して動作するが、0008適用後は共有上限が働く。旧Workerへのrollbackで上限や復旧gateが解除されるとは考えない。

| rolling 24時間の所有者枠 | 上限 |
| --- | --- |
| 画像（旧画像も1要求1枚として合算） | 10要求・20枚 |
| 動画 | 3要求・要求秒数30秒 |
| TTS | 10要求・入力20,000 UTF-8 bytes |
| 音楽 | 3要求・180秒 |
| 同時生成 | 所有者1件・環境3件（新旧合算） |
| 保存 | 所有者1 GiB・環境10 GiB。予約・保存済み・隔離・削除待ちを合算 |

画像は枚数×20 MiB、動画256 MiB、音声32 MiBを先に予約する。全期待素材の検査/保存receiptを確定してから実量へ置換する。部分回収は最大予約を保持する。失敗/取消も利用枠を消費したままとし、受付不明は同時数と容量も保持する。旧画像の活動中も最大1枚分の容量を計上するが、旧公開URLをprivate R2の保存実量と扱わない。これらは請求額の硬い上限ではない。

## 状態と競合

provider状態は`reserved/submitting/submission_unknown/queued/running/completed/failed/cancelled`、回収状態は`pending/collecting/collection_failed/stored/invalid/deleting/discarded`。取消意図は独立時刻として保持し、古いpollや遅い受付応答で消さない。

アプリ終端は、全期待素材の検査/保存完了、上流の失敗/停止確定、または完成した不要/不正出力の物理破棄確認時だけ。provider completed、取消受付、timeout、監視60分終了、部分回収を終端と扱わない。保存中に取消された場合は結果を公開せず、削除確認まで活動中/容量を保持する。

送信はattemptを1にするCASを1回だけ通す。未送信reservedは30秒lease切れを確実な失敗として終端化できるが、claim済みの不明要求は受付不明にし、再送しない。poll/回収は30秒leaseとtoken CASを使い、古い処理が新しい結果を上書きできない。provider処理は1回15秒の待機上限。driverにNo-Retry/fallback無効・開始期限120秒・Store-IO/非公開lifecycleの契約を渡すが、実falでの適用と回収可否は未検証。

回収の自動試行は最大3回、次の確認まで5/30/120秒を置く。再送は同じprovider IDの結果回収だけで、生成POSTを繰り返さない。上限後も未終端として保持し、後続の所有者による回収再開導線はM-2以降で具体化する。不正結果は成功にせず、破棄確認まで容量を保持する。

受付不明の解決は[内部の証拠照合境界](../src/server/media/retention.ts)だけに置く。運用者が当該上流要求の受付/未受付を照合し、確認できた同じprovider IDを紐付けるか、未受付確定を記録する。曖昧な証拠や期限経過では解放しない。公開の強制解除/再生成API、自動unknown解決はない。実上流の照合手順は工程Eで確認する。

## 本文消去・容量解放・復旧

本文はアプリ終端＋30日、本文なし要求/利用台帳は終端＋90日を起算点にする。再読込・回収再試行・消去要求で起算点を延ばさない。早期本文消去では入力JSON/入力素材リンクを消し、活動中なら取消意図を保持する。hash/要求識別/利用記録は90日まで残す。未終端/受付不明は日数経過で削除・枠解放しない。

容量は素材の物理削除を確認したときだけCASで解放する。ジョブ台帳を90日で消しても、削除未確認の容量記録と素材metadataは残す。これは本文/要求hash/消費台帳を延長して残す処理ではなく、残存objectの容量を失わないための独立した記録。R2の実削除・期限回収はM-2以降。M-1では信頼した内部adapterの確認境界をfakeで検証する。

定期処理に渡せるboundedな内部maintenance（1回100件）を用意した。今回はCron設定や常駐の回収処理を追加せず、実行者/schedulerとの結線は後続。従って未配備/停止中のDBについて、wall clock到達だけで物理消去が実施済みとは報告しない。期限後のHTTP本文取得はmaintenance前も拒否する。

DB復元前は新旧の有効化フラグだけでなく、全書込み・外部送信を止める。復元前の正しい本文なし利用/削除記録を承認済みの方法で確保し、復元後は再有効化前に復旧gateを閉じ直す。復元DBだけを正しい照合元と扱わない。gate自体も復元で巻き戻るため、DB外の停止を維持する。

内部reconcileは復元前の最小台帳との一致、早期消去/期限の再適用、上流側の照合確認を要求する。消費・容量・状態・旧画像の記録が不足/不一致、未解決ジョブが残る、または照合元がない場合はgateを解除しない。自動import/台帳削除/unknown解放で修復しない。上流/削除確認後の個別修復は別に承認する。検証境界は1000件まで（消去再適用100 statementまで）で、それ以上は手動の限定照合が必要。

30日は稼働DBの本文期限であり、D1 Time Travelやfal側コピーを含む全コピーの消去保証ではない。DB export/長期backup・復元直後の自動再送/再開は追加していない。Jevの本文/結果/hash非保存・終端90日・unknown消費/同時枠保持・自動再送/削除/解放なしは不変で、メディアのhash/ID契約を転用しない。
