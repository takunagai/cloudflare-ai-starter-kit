# 開発運用の改善と確認方法

確認日: 2026-10-07。対象は共通スターターと今回承認されたCodex共通指示・秘密保護の誤検知修正。実クラウド・モデル設定・実Secret・公開範囲は変更しない。

## 改善の目的

短い依頼を、関連の薄い再調査や再確認で長時間化させない。既存の保護と検証を維持しながら、依頼を完了するための作業と、本人に必要な次の行動を明確にする。

## 管理場所と更新範囲

| 対象 | 管理場所 | 扱い |
| --- | --- | --- |
| 通常作業の終了条件、質問と許可 | ユーザー共通のCodex AGENTS.md | 状況確認・文書・コミット・引き継ぎの範囲を明示。既読情報と同一版の成功済み検証を再利用 |
| 現在地と今回の許可 | [current-state.md](current-state.md) | 短く更新し、過去の状態を重ねない |
| 合意した仕様 | [architecture-proposal.md](architecture-proposal.md)と対象別の設定メモ | 状態報告を増やさず、契約を変更したときだけ更新 |
| 経緯と検証証拠 | [plan.md](plan.md)と工程別の記録 | 必要な論点だけ参照。完了済みの許可を新規実行へ転用しない |
| ソース名の誤検知 | ユーザー共通の秘密保護エンジンと合成テスト | Git公開前検査と同じ通常ソース名を扱い、dotenv/鍵/私有ディレクトリ/symlinkの保護を維持 |
| 失敗時の確認順 | [diagnostics.md](diagnostics.md) | 既存の固定理由から次の確認を選ぶ。診断のための無条件再送をしない |

## 作業の終了条件

- 文書変更: 直接関係する文書の意味、リンク、差分を確認して終える。仕様不変ならアプリの全検証を起動しない。
- コミット: 対象差分と検証済み版の対応を確認し、ステージ版・作者・公開検査・フックを通す。同じ検査を手動とフックで重ねるのは不足や必須規約がある場合だけ。依頼のないcommit/pushはしない。
- 障害調査: 最初に失敗した工程と失敗分類を確かめ、その候補を区別する検証だけを行う。原因未確定のまま「準備完了」「利用可能」と広げない。
- 本人への質問: 判断対象、推奨と理由、短い返答例、返答後の担当作業を本文に書く。操作なら画面/項目/期待結果も示す。選択UIを見たことを前提にしない。
- 継続: 許可済みの残作業はエージェントが続ける。判断が必要なら明示する。依頼完了後に新しい改善を提案するときは開始方法を添え、「操作不要」で放置しない。

## 確認ケース

| ケース | 期待する対応 |
| --- | --- |
| 「推奨の順序で進めて」 | 提示済み範囲の通常編集・検証を進め、毎工程の承認を取り直さない |
| 採用済みの構成について再開 | 記録と今回の対象/上限を照合し、同じ設計判断を取り直さない |
| 終了済みの30分窓を再利用したい | 新しい実行条件として扱い、旧許可を繰り越さない |
| 「表示した3択」が見えない | その場に選択肢と短い返答例を再掲し、本人の理解不足と扱わない |
| 本人が「準備完了」と報告 | 何の準備か不明なら対象だけ確認し、検索や配備成功と推測しない |
| ローカル改善完了、実配備は未許可 | ローカル完了と未配備を区別し、実配備が必要なら具体案と返答方法を提示 |

## 検証と次の評価

文書の構造・リンクと上記6ケースを確認した。再開入口は約1,700文字とし、README/構成資料の整理前本文と開発履歴の保持を内容比較で確認した。共通設定を含む対象14文書のローカル参照436件は欠落0。アプリコードは変更せず、無関係な全体checkや実クラウド試験は実行していない。

共通フックは4つの通常ソース名の誤拒否を合成入力で再現してから修正した。秘密保護17・限定検索5・Git公開前検査75テストが成功。さらにソース4名の許可と、ソース本文の疑似資格情報を拒否する境界2ケースを確認した。修正後、実ツール経路で通常ソース名を含むGit履歴の読み取りも成功した。秘密ファイル・資格情報の実値・公開例外は扱っていない。

時間短縮と応答の分かりやすさは未実証。次の実際の通常作業で、担当エージェントが経過時間、確認の往復数、不要な再読/再検証、手戻りを記録し、失敗した箇所だけ調整する。過去は主にGPT-6.1 Solの高〜極高を使用したという本人報告を前提にし、Astraだけを遅延原因としない。2026-10-08以降の担当はClaude Codeのため、評価はClaude Code側の通常作業で行う。
