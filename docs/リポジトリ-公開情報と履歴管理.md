# リポジトリの公開情報と履歴管理

開発履歴を残しながら、実環境情報を公開用ソースから分離する方針と手順。GitHubの非公開設定だけを情報保護の根拠にはしない。2026-09-28の履歴整理とPR #1・#2の実施記録は[archive](archive/リポジトリ公開情報の整理とPR運用の記録.md)にある。

## 保存先と扱い

| 保存先 | 内容 | 扱い |
| --- | --- | --- |
| `wrangler.jsonc` | ローカル設定・架空の配備例 | Git管理。実ID・AUD・公開先を含めない |
| `examples/presets/` | localとinternal/publicの各staging/production、計5断片 | 公開用。単独deploy不可、ダミーDB/例示origin/公開routeなし |
| `.wrangler.staging.local.jsonc` | 旧stagingの非Secret配備設定。2026-10-19に旧stagingとあわせて廃止し、手元からも削除した | Git管理外の除外指定は、誤って再作成された場合に備えて残す |
| `.wrangler.standard-staging.local.jsonc` / `.wrangler.production.local.jsonc` | 通常staging/production向けの完成設定の保管先 | Git/Biomeの除外を設定済み。実ファイルの作成は別承認の後に本人が管理し、共有しない |
| `docs/` | 方針・理由・変更時の注意・検証結果 | 本人メール・個別管理URL・実IDを残さない |
| `.publication-recovery/` | 整理前履歴の復旧用bundleと作業用データ | Git管理外・所有者のみアクセス。公開用ではない |

実配備設定と復旧フォルダはBiomeの対象からも明示除外しています。Git管理外だけでは他のツールの検査対象から外れるとは限りません。

Secretは配備設定にも書かず、人間が別ターミナルで投入します。以前追跡していたパッケージマネージャーのローカル設定ファイルと検証画像は公開用履歴から除外し、手元のファイルを維持します。

## 配備設定の選び方

通常の`pnpm check`・`pnpm build`は公開テンプレートを使い、環境選択を省略するとlocalです。次は通常stagingの例です。対象別の選択は[固定mode対応](公開プリセットとbuild境界.md#buildの選択と拒否)と[運用](operations.md#配備の手順)に従い、実設定の作成・build・dry-run・配備は別承認の後です。

```sh
CLOUDFLARE_ENV=staging pnpm build --mode standard-staging-local
WRANGLER_LOG_PATH=.wrangler/logs pnpm exec wrangler deploy --config dist/server/wrangler.json --dry-run
```

専用モードは手元の設定ファイルがないと失敗します。複製先で作者の設定を使い回さず、自分の承認済み対象へ設定してください。生成した`dist/`も実環境情報を含むためGit管理外です。実設定を使うbuild/dry-runの出力をPR・文書へ丸ごと貼りません。

dry-runを外すと実配備になります。公開用テンプレートをそのまま実配備してはいけません。

## 用途別設定の保存と共有

文書には公開例、キー名、設定方針、管理画面の辿り方だけを示します。実ID/AUD・team domain・個別管理URL・origin・リソース名・個人の運用構成は、非Secretでも公開許可が確認できなければリポジトリやPRへ記録しません。privateやスキャン検出0を公開許可の代わりにしません。必要な実値の保管先・共有範囲が未確定なら値を省略し、安全な準備を続けます。

通常stagingは別Worker/別DB、productionも専用DBを使う方針です。新しい管理外設定の不在時はbuildを停止し、公開断片への代替や作者の実設定コピーをしません。previewはflatten済み成果物で起動し、preview時の環境指定でretargetしません。生成物にも実運用情報が入り得るため、Git・文書・PRへ転記せず、元設定と同じ非共有の扱いにします。

別名複製は公開ソースの許可リストだけを使い、管理外設定・復旧領域・Secrets・ローカルDB・生成物・既存Git履歴を除外します。旧消費台帳の整理や削除、履歴書換え、例外/baselineの追加は行いません。

本書の保存方針とREADMEリンクは設定メモの正本として維持します。認証の利用者/session、実接続・公開範囲・費用を今後決めたり変えたりする場合は、確認日、理由、管理場所、影響、検証済み/未検証を該当docsへ残します。実値を記録するために未承認の操作を追加しません。

commit前はステージ内容、push前は送信対象の全コミットとメタデータ、PR等は送信本文を共通ルールに従って別確認します。過去の成功で免除せず、実運用情報の公開可否不明や検査不能が残る場合はその送信を止めます。フック設定・例外・baselineを検査通過目的で変更しません。

## メール設定とPR運用

GitHubのアカウント設定がPRの生成メタデータ（仮マージのauthor）に影響するため、PRを作る前に次を確認します。

| 対象 | 管理場所・方針 |
| --- | --- |
| Web操作の作者メール | GitHub → Settings → Emails → **Keep my email addresses private**を本人が有効にする |
| CLI pushのメール露出防止 | 同じ画面の**Block command line pushes that expose my email**を本人が有効にする。pushの最新コミットのauthorが非公開メールのときに拒否する仕組みで、全コミット・committerの検査の代わりにはならない |
| ローカルのauthor／committer | このリポジトリの`.git/config`の`user.name`・`user.email`に匿名設定を使う。globalの作者設定や他repoは変更しない |
| Git公開前フック | ユーザーの共通フックと検査実装。対象repoで実効hooksPath・hookファイル・エンジンの存在を確認する |

上の2項目はアカウント全体に影響するため、変更は本人が行います。メール値や設定画面の貼付は求めません。匿名設定では個人のcontributionへの紐付けを保証しません。明示的なauthor指定、Gitの環境による上書き、別clone・別PC・Web生成の履歴は別途確認が必要です。公式資料・採用理由・制約は[GitHubメール設定とPR参照の調査](../references/github-email-and-pr-safety.md)を参照してください。

### PRを送る前後の手順

1. 対象repoのprivate・ブランチ・PR・CIを再確認し、共通フックのstatusを対象repo内で検査する。未コミット変更を保持する。
2. 本人にEmailsの2項目の有効／無効だけを確認する。未確認・無効のままPR作成を先行しない。アカウント全体に影響する変更は本人が行う。
3. 次のauthor／committerが既存の匿名設定と一致するか、値を出さず判定する。ステージ全体、送信する全コミットの本文・メッセージ、各コミットの作者情報、PRタイトル・本文を別々に確認する。フックは作者情報・PR本文・サーバー生成参照の検査を代行しない。
4. 実際の文書変更を`codex/`ブランチにcommitし、共通フックを通して通常pushする。差分のない検証用PRは作らず、確認済み本文でドラフトPRを作成する。
5. PR作成後にGitHubから新しく参照を取得し、PRのheadと仮マージを明示的に含める。APIのtest merge先端と取得参照・親コミットが一致するか確認する。本文・メッセージとauthor／committerのメール・名前を分けて検査し、値ではなく種類・件数・判定を記録する。検査不能も停止扱いにする。
6. 最新headのブランチCIとPR CIを確認する。追加pushで仮マージが更新されたら再取得・再検査する。候補を検出したらmergeと追加送信を止め、値を再掲せず報告する。処理方法の判断前に例外登録・履歴書換え・force-push・削除を進めない。

### mergeの前後の確認

1. 対象PRのmergeが許可された範囲で、実差分とhead／baseの一致、最新headのCIを確認する。更新された差分は再レビューする。
2. readyへの変更で生成参照が更新される可能性も含め、最新仮マージを再取得・検査する。未解決候補や検査不能があればmergeと追加送信を停止する。
3. 履歴を保持する通常mergeでは、確認済みheadの一致条件を付けて取り込む。保護設定を変更・迂回しない。
4. merge後はAPIが実際のmerge先端を指すことを確認し、mainと残存PR参照を新規取得する。本文・メッセージとauthor／committerを別々に検査し、親・先端・履歴保持を確認する。
5. 実際のmain先端に対応する新しいCIを確認する。生成情報に新しい未解決候補があれば追加送信を止め、値を再掲せず報告し、取り込み済み履歴を無断で書き換えない。

検出0件やCI成功だけで漏えい不存在を保証しません。設定確認・ローカル検査・GitHub生成メタデータ・CIをそれぞれ区別して判断します。許可した範囲（表示名など）を、別の名前・個人メール・クラウド操作へ拡張しません。CIは`main`と`codex/**`へのpush、およびpull requestで実行されます。

変更時の注意:

- privateへ戻しても、公開中に取得された複製・fork・キャッシュは消えません。戻すだけで秘密の漏えい対応を済ませず、失効を確認します。
- 公開後は、push・PR・Issue・CIログがそのまま外部へ出ます。PR本文・Issue本文はGitフックの対象外なので、送る前に確認します。
- branch保護にPR必須やCI必須を加えると、mainへの直接pushが拒否されます。今の運用（mainへ直接push）を変えるときに合わせて判断します。force-pushを禁止しているため、履歴の書換えが必要になったら保護を一時的に外す判断も本人が行います。
- push protectionは秘密らしき文字列を含むpushをGitHub側で止めます。誤検出で止まっても、ローカルの公開ガードと同じく迂回せず原因を確認します。
- Dependabot security updatesは脆弱性修正のPRを自動で作ります。マージ前に、依存更新の確認手順（[運用手順](operations.md)）とCIを通します。

## 公開前チェックと限界

この作業環境では共通Gitフックがインデックスとpush対象の全コミットを検査します。秘密ファイルの閲覧を防ぐエージェントのフックとは役割が異なります。別PC・CIへ自動配布される仕組みではありません。

公開範囲を変える操作は、そのつど本人が判断します。検出0件は未知の秘密・自由文の個人情報・第三者コピーがない保証ではありません。公開前に全ブランチ・タグ・PR本文・CI成果物と運用記録を確認してください。実Secretの露出には履歴削除とは別に失効確認が必要です。

根拠: [GitHubの機密情報削除手順](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)、[git-filter-repo](https://github.com/newren/git-filter-repo)。
