# リポジトリの公開情報と履歴管理

確認日: 2026-09-28。開発履歴を残しながら、実環境情報を公開用ソースから分離します。GitHubの非公開設定だけを情報保護の根拠にはしません。

## 保存先と扱い

| 保存先 | 内容 | 扱い |
| --- | --- | --- |
| `wrangler.jsonc` | ローカル設定・架空の配備例 | Git管理。実ID・AUD・公開先を含めない |
| `.wrangler.staging.local.jsonc` | 既存stagingの非Secret配備設定 | Git管理外・所有者のみ読書き。共有しない |
| `docs/` | 方針・理由・変更時の注意・検証結果 | 本人メール・個別管理URL・実IDを残さない |
| `.publication-recovery/` | 整理前履歴の復旧用bundleと作業用データ | Git管理外・所有者のみアクセス。公開用ではない |

実配備設定と復旧フォルダはBiomeの対象からも明示除外しています。Git管理外だけでは他のツールの検査対象から外れるとは限りません。

Secretは配備設定にも書かず、人間が別ターミナルで投入します。以前追跡していたパッケージマネージャーのローカル設定ファイルと検証画像は公開用履歴から除外し、手元のファイルを維持します。

## 配備設定の選び方

通常の`pnpm check`・`pnpm build`は公開テンプレートを使います。既存stagingの配備成果物が必要なときだけ、次を選びます。

```sh
CLOUDFLARE_ENV=staging pnpm build --mode staging-local
WRANGLER_LOG_PATH=.wrangler/logs pnpm exec wrangler deploy --config dist/server/wrangler.json --dry-run
```

専用モードは手元の設定ファイルがないと失敗します。複製先で作者の設定を使い回さず、自分の承認済み対象へ設定してください。生成した`dist/`も実環境情報を含むためGit管理外です。実設定を使うbuild/dry-runの出力をPR・文書へ丸ごと貼りません。

dry-runを外すと実配備になります。今回の整理では再配備・DNS変更・Secret投入をしていません。公開用テンプレートをそのまま実配備してはいけません。

## 履歴整理の方法と影響

- 既存8コミットの順序・時刻・説明を保ち、実環境の識別子・個別URL・個人パスを置換します。文書内のゼロID・例示用ドメインは照合値ではありません。
- author/committerを匿名化します。ハッシュは変わり、旧署名・旧URL・古いcloneとの連続性は維持できません。
- 画像と秘密ファイル名の追跡ファイルは、公開可とみなさず履歴から除外します。認証テストの固定値は用途を区別した架空値へ置換します。
- 古いclone・bundle・PR参照・CIログは最新ファイルの削除だけでは消えません。古いcloneからmerge/pushすると元の履歴が再混入するため、更新後は新しくcloneしてください。
- 元の履歴は復旧のため手元だけに保全します。復旧不要と判断するまで共有しません。

## 公開前チェックと限界

この作業環境では共通Gitフックがインデックスとpush対象の全コミットを検査します。秘密ファイルの閲覧を防ぐエージェントのフックとは役割が異なります。別PC・CIへ自動配布される仕組みではありません。

GitHubの公開切替は今回行いません。検出0件は未知の秘密・自由文の個人情報・第三者コピーがない保証ではありません。公開前に全ブランチ・タグ・PR本文・CI成果物と運用記録を確認してください。実Secretの露出には履歴削除とは別に失効確認が必要です。

結果と残る制約は[進捗](plan.md)・[作業ログ](staging-work-log.md)へ追記します。

根拠: [GitHubの機密情報削除手順](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)、[git-filter-repo](https://github.com/newren/git-filter-repo)。

### 前回の整理時にPRを保留した理由

最初の再作成時にドラフトPRを作ると、GitHubが生成した仮マージコミットのauthorに非公開メール候補が入りました。ローカル履歴の匿名化だけでは防げないため、そのリポジトリも作り直し、当時はPRを作成しませんでした。特定のアカウント設定が原因とは確定していません。CIは `main` と `codex/**` へのpushで実行できます。

今後PRを作成する前に、本人がGitHub → Settings → Emailsのメール非公開設定を確認してください。CLIの作者設定とGitHub側の自動生成コミットは別です。確認できていない状態でPRを作成せず、必要なら非公開の検証用リポジトリで生成メタデータも確認します。前回の整理時はアカウント全体の設定を変更していません。

GitHubのWeb操作と手元のGitでは作者メールの設定場所が異なります。根拠: [公式のコミットメール設定手順](https://docs.github.com/en/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address)。今回の本人設定確認・操作は下記へ記録します。

### PRを送る前後の手順

1. 対象repoのprivate・ブランチ・PR・CIを再確認し、共通フックのstatusを対象repo内で検査する。未コミット変更を保持する。
2. 本人にEmailsの2項目の有効／無効だけを確認する。未確認・無効のままPR作成を先行しない。アカウント全体に影響する変更は本人が行う。
3. 次のauthor／committerが既存の匿名設定と一致するか、値を出さず判定する。ステージ全体、送信する全コミットの本文・メッセージ、各コミットの作者情報、PRタイトル・本文を別々に確認する。フックは作者情報・PR本文・サーバー生成参照の検査を代行しない。
4. 実際の文書変更を`codex/`ブランチにcommitし、共通フックを通して通常pushする。差分のない検証用PRは作らず、確認済み本文でドラフトPRを作成する。
5. PR作成後にGitHubから新しく参照を取得し、PRのheadと仮マージを明示的に含める。APIのtest merge先端と取得参照・親コミットが一致するか確認する。本文・メッセージとauthor／committerのメール・名前を分けて検査し、値ではなく種類・件数・判定を記録する。検査不能も停止扱いにする。
6. 最新headのブランチCIとPR CIを確認する。追加pushで仮マージが更新されたら再取得・再検査する。候補を検出したらmergeと追加送信を止め、値を再掲せず報告する。処理方法の判断前に例外登録・履歴書換え・force-push・削除を進めない。

今回の作業にはmerge・公開切替・リポジトリ削除／再作成・履歴再書換え・GitHub保護設定変更を含めません。新しい検証用repoが必要になった場合は対象・目的・後処理を具体化して本人に確認します。検出0件やCI成功だけで漏えい不存在を保証しません。設定確認・ローカル検査・GitHub生成メタデータ・CIをそれぞれ区別して判断します。

公式資料・採用理由・制約は[GitHubメール設定とPR参照の調査](../references/github-email-and-pr-safety.md)を参照してください。
