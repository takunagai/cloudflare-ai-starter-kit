## 次の操作

以下は導入者がローカル確認を行うときの順序です。このセッションでの実行許可や、実設定を持つ作業端末での起動指示にはしません。別プロジェクトへのコピー・名称変更・空DB検証は[工程D](../用途別プリセット-開発計画.md#別名クリーン複製の手順と証拠)で別に扱います。

1. `.node-version`と`package.json`に合わせてNode.js 26.10.0 / pnpm 12.6.0を用意します。グローバル環境は自動変更しません。

   ```sh
   node --version
   pnpm --version
   ```

2. 固定依存をインストールします。lockfileやoverrideを更新しません。

   ```sh
   pnpm install --frozen-lockfile
   ```

3. このプロジェクト自身のdev/previewを停止した状態で、ローカルD1へ未適用SQLを適用します。`--remote`は使用せず、適用済みSQL・旧台帳は変更しません。

   ```sh
   pnpm db:migrate:local
   ```

4. 環境選択を省略したローカル作業端末で起動します。`CLOUDFLARE_ENV`を空文字や`local`にして代用するとbuild境界で拒否されます。別環境が解決される場合は停止し、[mode対応](../公開プリセットとbuild境界.md#buildの選択と拒否)を確認します。環境dumpで診断しません。

   ```sh
   pnpm dev
   ```

5. [ローカルアプリ](http://127.0.0.1:3000/app)で、架空の`tester@example.invalid`と他用途に使わないテスト用パスワード（12〜128文字）を使って登録します。「動作確認用の固定応答（AI未使用）」を選び、送信、再読み込み、会話選択による復元、会話削除、logoutを確認します。固定応答を実AIの結果として扱いません。
6. HTTP確認が必要なら、別ターミナルで`pnpm smoke 3000`を実行します。HTTP smokeは画面のhydrationやクリックを保証しません。終了は起動ターミナルのCtrl+C。ポート競合時は既存の別作業プロセスを停止しません。

build済み成果物の確認が必要なら、同じlocal対象で`pnpm check`→`pnpm preview`、別ターミナルで`pnpm smoke`の順です。previewはflatten済みのbuild成果物を使い、preview時の環境指定で別環境へ切り替わりません。Viteの`production` mode名だけでは`APP_ENV=production`になりません。

ローカルDBには架空アカウント・利用台帳が残ります。smokeの会話削除を全データ削除と扱わず、既存DBを無断で消しません。通常テストの一時DBとは区別します。
