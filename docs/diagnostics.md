# 失敗時の診断と次の確認

確認日: 2026-10-07。既存の実装・合成試験を参照した運用設計。新しい実接続や再試行を許可するものではない。

## 最初にすること

担当エージェントが、失敗した工程、確認済みの状態、未確認の状態を分ける。本人への案内は「何が起きたか」「いま何をするか」「その結果で次に何を進めるか」の順にする。

1. 受付、上流実行、結果回収、保存、表示、課金/削除のどこまで確認できたかを、既存の台帳/固定分類で確認する。本人が見た画面だけで上流処理や未課金を断定しない。
2. 下表から原因候補を区別できるローカル確認を選ぶ。既にある分類を先に使い、同じ検査や同期・送信を理由なく繰り返さない。
3. 必要な証拠が残っていなければ原因未確定とする。次回用の診断を合成データで検証してから実行案を作る。新しい実送信は別の許可が必要。

## 工程Eの回収拒否

所有者にだけ返す`/api/media-probe`の`job.invalidReason`を使う。[image-driver.ts](../src/server/media/image-driver.ts)の分類と[回収試験](../tests/media-image-driver.test.ts)、[専用経路試験](../tests/media-probe.test.ts)を対応させる。

| 固定分類 | 分かること | 次に担当エージェントが確認すること |
| --- | --- | --- |
| `result_shape` | 結果の構造が受入schemaに合わない | 固定endpointのschemaとnullable/任意項目の差。ダミーの応答で再現する |
| `result_count` | 画像数が要求と合わない | 要求枚数と応答配列の契約。再生成で埋め合わせない |
| `url_policy` | 取得先が許可条件に合わない | 公開仕様の配信元とURL検証条件。実URLを記録せず、ダミーURLで境界を検証する |
| `duplicate_url` | 同じ取得先が複数含まれる | 配列の重複をダミーで再現し、上流仕様との対応を確認する |
| `image_bytes` | 実画像が受入条件に合わない | 形式・実寸法・透過・容量の判定を合成画像で確認する。特定の条件が原因だったとは断定しない |
| `null`で終端が`invalid` | 古い版などで理由が残っていない | 配備版とmigrationの証拠を照合する。今回の原因を推測で補わない |

## 短期token・自然期限の観測

`evidence[].diagnostic_reason`を使う。分類は[probe-diagnostics.ts](../src/server/media/probe-diagnostics.ts)、保存制約は[0014](../migrations/0014_media_probe_observation_reason.sql)を参照する。実値や生レスポンスを追加取得して説明しない。

| 固定分類 | 分かること | 次に確認すること |
| --- | --- | --- |
| `initial_owner_unreadable` | 期限前の所有者取得を確認できない | token応答の形式、有効期限の解釈、ACLと取得処理のダミー試験 |
| `fresh_token_unreadable` | 新tokenでも正常取得を確認できない | 期限切れ試験の比較対象が成立していない。新token側と通信失敗を先に切り分ける |
| `expired_token_readable` | 期限後の旧tokenで取得できた | 有効期限の解釈と観測時刻。期限後拒否の成功と扱わない |
| `expired_token_other` | 期限後応答が想定する拒否でも正常取得でもない | リダイレクトや他の応答の扱いをダミーで再現する |
| `owner_token_denied` | 自然期限の確認で所有者認証が拒否された | 認証拒否とファイル消去を分ける。消去成功とは判断しない |
| `media_still_readable` | 自然期限の観測時に取得できた | 保持条件と起算時刻を確認する。実際の消去時刻は断定しない |
| `other_response` | 自然期限の確認が既知の分類に合わない | 固定分類を追加する必要性を検討し、合成試験で区別する |
| `observation_error` | 通信・中断・上限・DB等を含む観測処理の失敗 | 既存の回数/状態と実行経路を照合する。この分類だけで通信失敗と断定しない |

過去runの個別HTTP状態は残っていない。0014の未配備版を既存runへ適用しても、過去の原因が復元されるわけではない。UIは判定中心で、上表の分類を詳しく案内する画面は未実装。運用担当は許可済みの所有者API/台帳の必要項目だけを使う。

## 次に診断を実装するときの条件

- 固定された工程名、理由、状態、回数など、問題を区別する最小項目だけを使う。本文、token、Cookie、鍵、実URL/ID、丸ごとのエラーをログへ残さない。
- 最初に記録項目と判定の対応を決める。同じ事象を何度見ても原因候補が減らない分類では、診断完了としない。
- 利用者向けの「次にすること」と内部の固定分類を分ける。再送の可否は受付/消費/冪等性の証拠で決め、表示だけで新しい要求を送らせない。
- 正常系に加え、結果は返ったが不適合、上流受付後の切断、保存失敗、診断自体の失敗、所有者外の参照拒否を検証する。新しい分類が秘密を返さないことも確認する。
- 原因を調べるための枠復活、受入条件の緩和、無条件再試行は追加しない。

この設計は共通スターターが対象。派生した資料検索チャットの検索品質・初回失敗や配備helperの修正は、複製先自身の未解決事項として扱い、本書の整備で解決済みにしない。
