# チャット・履歴・承認付きツール

`src/server/chat.ts`、`chat-store.ts`、`agent-tools.ts`が実装の正本。通常CIは外部AIを呼ばず、Workers内でD1とSDK経路を検証する。

## データと権限

ブラウザは会話ID・要求UUID・許可モデルID・今回の本文だけを送る。利用者IDと過去メッセージはサーバーがセッション/JWTとD1から取得する。別ユーザーの会話・承認・メモは取得も変更も拒否する。

会話作成・取得・一覧・削除、モデル選択、生成中止、失敗状態を画面で扱う。再読み込み後は一覧の会話を選ぶと履歴が復元される。公開ページと`/app`のSSRに非公開データを埋め込まず、認証後のAPIは`no-store`。モデル出力とメモはReactの文字列描画で表示し、任意HTMLを実行しない。

会話を削除すると本文・出典は削除する。**利用台帳`chat_requests`は残す**。会話IDをNULLにして、日次枠と重複要求の記録が会話削除で消えないようにする。台帳は利用者ID、要求UUID、モデル、入力ハッシュ、時刻、状態を持ち、本文を持たない。履歴保持期間とアカウント削除時のデータ消去は複製先の利用規約に合わせて追加する。

## 上限と再試行

| 項目 | 標準上限 |
| --- | --- |
| 会話数 | 利用者ごと100件 |
| 今回の入力 | 8,000文字、JSON body 40,000 bytes |
| 過去の文脈 | 完了済み最大20メッセージ、合計16,000文字 |
| モデル出力 | 各step 1,024 tokens、表示/保存全体16,000文字 |
| チャット受付 | 利用者ごと10回/分、60要求/UTC日、同時1件 |
| 認証後API | 利用者ごと120回/分 |
| 推論deadline | 60秒。AbortSignalで中断 |
| 予約の回復 | 120秒を過ぎたpendingをfailedにする |
| tool有効時 | 最大3モデルstep、最大4tool実行、保存には別途人間承認 |

厳密な日次予約と同時実行の判定はD1の同じtransactionに含める。受付済みの失敗・中断も日次枠に数える。要求IDが同じ完了済み入力は再生成せず履歴を返す。処理中、内容が異なる再利用、失敗IDの再利用は409。新しい試行は新しいUUIDと利用枠を使う。

自動モデルretryは0回。通信断・中断・deadline後も上流処理や課金が止まる保証はない。プロバイダー側の予算・請求上限も設定する。日次回数は金額上限ではなく、toolモードの1要求には最大3回のモデル呼出しが含まれる。

SSEは`start`→（RAG有効時は`sources`）→`delta`→`finish`。失敗時は固定の`error`コードを送り、途中本文をfailed/cancelledで保存する。履歴保存に失敗した場合は完了表示せず`history_save_failed`とし、残った予約は期限後に回復する。SDK例外、入力、認証情報はログへ出さない。ページ再読込によるストリーム途中からの再開は対象外。

## 要求台帳と再送

通信断やストリーム中断の後に同じ入力を再送して二重に推論・課金しないよう、要求ごとの台帳と失敗分類を持つ。管理場所は`migrations/0015_chat_reliability.sql`、`src/lib/reliability.ts`、`src/components/request-recovery.ts`。

- 台帳`chat_requests`は`inference_started`（新規要求は0、モデル呼出し直前に1）と`failure_code`を持つ。1は推論が始まった可能性で、課金済みの証明ではない。印を永続化できなければモデルを呼ばない。0015適用前の既存要求はNULLのまま残し、推論なしと推定しない。
- 失敗は段階ごとに固定分類する。推論前: `history_read_failed`、`request_preparation_failed`。推論後: `generation_failed`、`generation_cancelled`、`generation_timeout`。保存不明: `history_save_failed`。再利用: `request_in_progress`、`request_already_used`、`request_id_conflict`。文言の正本は`FAILURE_MESSAGES`で、上流の生エラー・本文・資格情報を含めない。
- `GET /api/chat/requests/:requestId`は認証済み所有者の受付記録だけを返す（`status`、`inference`、`failureCode`、`canRetry`）。120秒を超えたpendingは`unknown`。`canRetry`は推論前の失敗だけtrue。検索・推論は呼ばない。
- ブラウザは送信前に利用者ごとの要求IDと会話IDだけをlocalStorageへ記録する。本文・回答・出典は保存しない。再読込後も結果未確認なら新しい送信を止め、「要求の状態と履歴を確認」で台帳と履歴を照合する。完了確認、または推論前失敗を確認した本人の入力再開で記録を消す。記録できないブラウザでは送信しない。受付前に確定した4xx（入力不正・未知モデル・上限等）は台帳に残らないため記録を消す。
- `api()`はfetch失敗を`network_unconfirmed`、401/redirectを`authentication_required`、非JSON応答を`unexpected_response`に分類する。

履歴APIは最新1,000メッセージを返す。長大な履歴のページングや検索は複製先で追加する。日次枠台帳を不用意に削除しない。分単位のAPI counterは期限後のリクエストで掃除する。

## RAG

`ENABLE_RAG="true"`にした構成ではチェックを入れて検索付き回答を選べる。検索queryは今回入力の先頭2,000文字、返却候補は5件、モデルへ渡す参考本文は16,000文字まで。検索には拡張共通の日次60回上限がある。

資料や検索結果を命令として扱わず、所有権を確認した断片だけをモデルへ渡す。出典IDを示すようモデルへ指示し、画面でタイトルと該当断片を確認できる。出典断片は回答と一緒に履歴へ保存する。原本削除後も既存会話の断片は残るので、消去対象なら会話も削除する。引用の正確性を機械的に保証する構成ではない。AI Searchの非同期索引と追加設定は[拡張手順](extensions.md)を参照。

## 人間の承認付きメモ

`ENABLE_AGENT="true"`だけで有効化でき、RAGや外部リソースの追加は不要。モデルに許可するのは、所有者限定の`searchNotes`と`draftNote`の2つだけ。

1. toolを有効にしてチャットする。モデルが既存メモを検索し、必要ならタイトルと本文を提案する。
2. 提案を「承認待ちのメモ」で確認する。`draftNote`は提案レコードだけを作り、保存済みメモは変更しない。
3. 人間が保存を承認すると、同じIDでメモを一度だけ保存する。拒否・期限切れ・別利用者の承認は保存しない。期限は24時間。

引数はZodで検証し、未知のtool名を実行しない。メモ本文も未信頼のデータとして扱う。モデルが「承認した」と書いても保存権限は付与されない。外部送信・任意コード実行・ファイルアクセスのtoolは提供しない。

## 実装上の判断

Better Authの永続化はDrizzleを使い、チャットの原子的予約・承認競合は明示SQLとD1 batchで表す。汎用repositoryや独自plugin基盤を追加しない。ブラウザはReactとFetchの小さなSSE consumerで構成し、モデル接続はAI SDKに集約する。
