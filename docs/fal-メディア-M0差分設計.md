マスクは先頭素材ID/版と明示的に紐付け、画像と同じ寸法のPNG・alphaありを要求する。透明領域と保持領域の例をUIに表示する。自動リサイズ、画像の並べ替え、マスクの別画像への付け替えはしない。PNG同士の条件は保守的なアプリ契約で、編集結果がマスクに厳密一致する保証ではない。

## 保存期間・認証配信・削除

推奨する専用`MEDIA_BUCKET`はprivateとし、RAG資料bucketと分ける。AI Searchの索引や公開r2.dev/custom domain配信には使わない。これはbinding名案であり、実リソースは作成していない。素材IDは不透明ID、object keyはサーバー専用とし、IDだけで閲覧権を与えない。

- 参照素材の期限は検証完了時刻＋7日。生成物は最初の回収保存時刻＋30日。同じ素材の再利用・再読込・回収再試行で期限を延ばさない。生成画像を動画へ渡す際も同じID/期限を使い、参照用コピーで延命しない。
- 生成画像の再利用時も、参照用の形式・10 MiB・寸法/画素・要求合計容量を再検査する。出力として保存できても参照上限を超える画像は素材選択を不可にし、理由を表示する。自動縮小・再符号化・再生成は初版に追加しない。
- 認証配信はsession検証→所有者一致→ready/期限/削除確認→R2読出し。全応答はprivate/no-store、同一originのみ。未認証/他所有者にはobject key・サイズ・ETagを返さない。失効はD1時刻で即時拒否する。
- 削除要求は素材をtombstone化し、取得grantを失効させ、新しい生成への参照を拒否する。実行中ジョブには取消を要求できるが停止を保証しない。上流へ既に渡ったデータや開始済みstreamは取り戻せない。
- R2削除の成功を確認してから保存容量を解放する。失敗は削除待ちとして再試行し、一覧から隠しただけで物理削除済みとしない。D1とR2を跨ぐ原子性はないため、冪等な削除状態を保持する。
- 同じWorkerの定期処理で期限切れ/孤立object/削除待ちを回収する案。1分ごとにジョブ10件・削除20件などのbounded batch＋D1 leaseを使う。R2 lifecycleの7日/30日prefixルールは補助とし、通常24時間程度の削除遅延があるためアクセス判定には使わない。設定や定期処理は今回作成しない。

ジョブ入力のprompt/台詞/参照は所有者だけが閲覧可能なDB情報。推奨は終端から30日で本文/出力URL等を消去し、本文を含まない利用量・冪等性記録は90日保持する案。素材の7日/30日と異なるため、採用前に用途・削除要請・DBバックアップの保持も確定する。ログへ本文・取得トークン・provider URLを出さない。

音声/動画は認証後に単一Rangeを扱う。通常200、成功206とContent-Range/Accept-Ranges/正確なContent-Length、範囲外416と`bytes */size`を返す。`bytes=start-end`/末尾省略/suffixを検証し、複数Rangeは初版では416。HEADは本文を返さず、Rangeによる部分本文を作らない。If-Rangeは強いETag一致時だけ部分配信し、不一致/弱い値は全体200へ戻す。初版は304最適化を必須にせず、どの経路も認証を先に行う。R2 range streamと切断時の解放、seek再生、期限直後の再要求をM-3/M-4で検証する。

## falが取得する参照画像の経路

**構成は採用確認待ちの推奨案。** 新しい通常環境の主Workerに`/api/media-source/:grantId`を設け、このパスだけアプリsessionの代わりに短期capabilityで認証する。主アプリ全体を公開しない。R2のS3署名URLは別資格情報と失効の制約があるため初版の推奨にはしない。

1. 認証済み生成要求の所有者・素材ready/期限・model/role・容量/利用枠を確定する。クライアントが送るのは素材IDでありURLではない。
2. 所有者・ジョブ・素材ID/版・用途（falへの参照入力）・GET/HEAD・有効期限に束縛したgrantを作る。256 bitのランダムtokenを生成し、DBにはhashだけ保存。URLには実object keyや利用者IDを含めず、query tokenをログ・履歴応答・分析へ残さない。
3. TTLは30分を推奨。素材の残り期限が30分未満なら送信前に拒否する。queue開始待ちの上限を120秒に制限する案だが、providerの素材取得時刻を保証するものではない。有効期限を自動延長しない。
4. providerの複数回取得に備え単回利用にはしない。grantあたりGET20回・累積転送量は素材容量の10倍までを原子的に予約する案。HEADにも別の回数制限を置く。Range付きprovider要求の要否はM-2/Eで確認し、初版の画像経路では未対応として拒否する。
5. grant照合後も素材とjobの所有者/版/削除/期限を再検査する。取消・削除・取得完了・期限到達で失効。受付不明時は自動延長や新規生成をせず、最大TTLで自然失効させる。

Accessはより具体的なpathのpolicyが優先されるが、**現行のWorker全体保護がそのままこの構成に使えるとは仮定しない**。新しい通常環境でpath別のSelf-hosted applicationを設計し、取得pathだけ対話ログインを外してWorker内のcapability検証を必須にする。prefix解釈、末尾slash、URL encoding、別hostname経由、Accessなしの直アクセス、tokenなし/期限切れを検証する。アクセスログ/traceのquery保存も設計対象。既存検証stagingのAccess/Worker/DBは変更しない。

この構成の採用は公開URLの開設やAccess変更の実行許可ではない。M-2ではfake fetchで契約を検証し、外部から到達可能な取得経路・fal側取得は工程Eで別承認する。loopbackをfalへ公開するトンネルは追加しない。

## 生成要求・結果回収・上流保存

provider状態とアプリの回収状態を分離する。例: providerは`submitting/queued/running/completed/failed/cancel_requested/submission_unknown`、回収は`pending/collecting/collection_failed/stored/invalid`。上流completedだけでアプリの保存完了を表示しない。全期待素材が検査・保存できてから完了とし、部分成功はそのまま履歴へ残す。

- 初回送信前に所有者＋client request IDと正規化入力hashを保存。同ID/同入力は既存jobを返し、同ID/異なる入力は409。同じ生成を重複POSTしない。
- SDKを使う場合も自動retryは0、falへ`X-Fal-No-Retry: 1`と`x-app-fal-disable-fallback: true`を送る案。別endpointへの自動転送も止める。送信timeout/5xx等で受付不明なら`submission_unknown`として枠を保持する。利用者の再読込や再試行で新しい生成を行わない。確認/解決手順をM-1で用意する。
- status/result/cancelはcatalogに登録したqueue経路と保存済みrequest IDから構築する。応答中の任意URLをそのまま呼ばない。1fetch timeout15秒、poll間隔5〜30秒、総60分を監視上限案とし、超過は状態不明・枠保持にする。処理継続は上記lease付き定期処理を使い、単一HTTP接続に依存しない。
- 生成結果は型（images[]/video/audio）、件数、HTTPS URL、許可host/path、redirect拒否、実形式、容量、寸法/再生時間を検証してR2へbounded streamで保存する。JSONサンプルのimage/pngや空URLを音声/動画の正解としない。
- 回収失敗は同じrequest ID・同じ結果だけを5/30/120秒間隔で最大3回再試行する案。その後も期限内なら所有者が回収を再実行できる。assetのjob/ordinalとobject keyを一意にし、保存済み分を再作成しない。形式不正/上限超過はinvalidとして、再生成を誘発しない。
- cancel要求の受付を停止・返金・未課金の証拠にしない。取消後に結果が完成した場合は、所有者の削除意図を保持して不要コピーを回収/削除する処理を別状態で扱う。

fal側保存はアプリのprivate R2と別契約。推奨は`X-Fal-Store-IO: 0`（JSON入力/結果の保持抑制）と`X-Fal-Object-Lifecycle-Preference`の`expiration_duration_seconds: 3600`および`initial_acl: { default: "forbid", rules: [] }`。ただしStore-IO=0で非同期結果回収を維持できるか、12 endpointすべてでACL/expirationが適用されるかは未検証で、対応済みとはしない。回収期限は上流の実際の期限と1時間の短い方とし、余裕を残して回収する。

ACLの対象はfal CDN v3。制限されたファイルはFAL_KEYそのものでは取得できないため、サーバーが固定の`rest.fal.ai/storage/auth/token?storage_type=fal-cdn-v3`で短期token（推奨300秒）を取得し、許可したCDN v3経路だけにBearerを付ける設計。redirect・別hostへ資格情報を送らず、tokenをDB/クライアントへ保存しない。モデルが別CDNを返す場合や制限不能の場合は回収エラーとし、黙って公開保存へ切り替えない。公開出力を許容する別方針は未採用。

出力後の拒否だけでは上流での公開を防げない。従ってprivate出力/期限を確認できないendpointは実利用の許可一覧へ加えず、Eの別承認では公開可能な合成素材で先に検証する。ローカルfake成功だけで実素材の送信を解禁しない。

Store-IO=0はCDNファイルの削除を意味しない。falの削除APIやアプリの削除だけで入力コピー・内部保持・バックアップが全て消えたとも扱わない。上流のデータ取扱条件、実際の匿名取得拒否、回収tokenの期限、期限後の削除は工程Eの検証条件とする。削除契約を満たせない素材を実送信しない。

## 旧画像ジョブと追加migration案

既存`image_jobs`、FLUXのAPI入出力、既存0001〜0006は変更しない。新しい`media_jobs`系を追加し、既存データを書き換えず履歴adapterでlegacyとして表示する。旧provider URLの保存をprivate R2で回収済みと表示せず、旧画像の有効期限・取得不能はそのまま示す。過去URLの無断取得・コピーは行わない。

新規設定候補は`ENABLE_MEDIA="false"`と`MEDIA_ALLOWED_MODELS`（12固定IDの部分集合JSON配列）。旧`ENABLE_IMAGES`は旧経路用に保持し、互換性を壊して12モデルへ自動転送しない。新旧の同時利用も所有者/環境の共通枠を適用し、request IDの衝突は拒否する。media OFFは新規生成/アップロード停止とし、所有者による既存素材の閲覧/削除/回収/取消の扱いは操作別に定義する案。旧APIの既存404等は維持する。AI_MODE/JEV_MODEの一括停止対象へfalを自動追加しない。

| 追加テーブル案 | 主な項目・不変条件 |
| --- | --- |
| media_jobs | id、owner_id、client_request_id、input_hash、model_id/catalog版、種別、入力JSON、provider request ID、provider/回収状態、各時刻、lease。owner＋client request ID一意。生のtokenは保存しない |
| media_assets | id、owner_id、object_key/版、source/upload/result、形式/bytes/寸法/秒数、状態、expires_at/deleted_at。object_key一意。IDの再利用/上書き禁止 |
| media_job_assets | job/asset/owner、role（reference/start/end/mask/output）、ordinal、mask対象。複合外部キーで同一ownerと順序を保証 |
| media_asset_grants | id、token_hash、job/asset/owner/版、用途、expiry/revoked_at、転送回数/bytes予約。token hash一意、素材削除時に失効 |
| media_storage_reservations | owner、upload/jobに束縛した予約、予約bytes/状態/期限。実保存量＋予約量の上限を原子的に検査。回収や削除の再実行で二重解放しない |
| media_usage_events | owner、job、種別、数量/秒数/入力量、消費時刻。失敗を含む予約消費の一意性とrolling窓を保持。本文なし |

schemaとSQLはM-1でレビューし、**実装時点の次の空き番号**を使う。0007はB-3Jが先に使用する可能性があるため本書では予約しない。D1 transaction/batchとCASを使う具体的な予約SQL、外部キーとindex、孤立回収、本文消去後の冪等性保持期間をM-1前に確定する。新SQLファイルの作成・local/remote適用は今回なし。

migration検証は空DB、0001〜0006済みで旧画像ジョブ/検証台帳が存在するDB、適用済み再実行、途中失敗を対象にする。旧データのID/所有者/状態と検証消費台帳が変わらないこと、旧Workerが追加tableを無視して動けることを確認。追加tableを削除してrollbackする手順を標準にしない。
