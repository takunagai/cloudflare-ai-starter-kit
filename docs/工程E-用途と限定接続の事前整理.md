2. `reserveMedia`の新規job/body・既存triggerによる利用/20 MiB容量予約と、probe attempt挿入/総消費加算を**1つのbatch**へ統合する。probeのBEFORE INSERT triggerでrun/slot/owner/hash/版、DBの現在時刻、used<2、停止なし、1回目判定を検査し、違反はRAISE(ABORT)。AFTER INSERTで総消費と状態を単調更新。影響行0やtrigger不適合を成功扱いせず、どちらの予約だけでもcommitしない。通常jobはこの専用記録を作れない。
3. 今回はmanifest/slot照合で2回目を常に拒否する。将来別承認でslot 2を登録する場合も、triggerは1回目の終端・全必須項目pass・本人の品質適合と費用照合・未解決unknownなしをDBで再検査する。`stored`だけ、ブラウザの「成功」、共通同時枠解放だけでは通さない。複数タブ・同時POSTでもslot一意/triggerで1件だけ予約する。
4. dispatchは共通`claimMediaSubmission`とprobe claimを原子的に組み合わせる。attempt_count=0→1を一度だけ更新し、同じrun/slot/job/lease、停止/期限/復旧状態を再照合。**DB commit確認後にだけ**生成POSTを開始する。commit応答が不明なら送らず停止、既にcommitしていた消費は残す。
5. transportの生成POST直前にも承認・DB時刻/停止revisionを再検査し、固定ヘッダーを送る。期限末尾15秒は新規dispatchを拒否する保守的余裕案とし、最後の検査とfetch開始の間に追加の非同期処理を置かない。30分窓はWorkerからの新規POST開始の許可期限で、上流の受付/実行終了時刻の保証ではない。D1 transactionと外部fetchは原子的にできないため、停止と競合して既にclaimされた1件は送信済みまたはunknownとして扱い、停止APIで無送信を保証しない。
6. 予約commit後の未送信失敗・上流失敗/取消・timeout/5xx/不正ack/provider ID保存失敗も総消費を返さない。dispatch開始後の不明は`submission_unknown`、総消費・同時枠・最大容量を保持。未送信が確定した場合だけ既存契約で同時/容量を解放しても、probe総消費は減らさない。生成POSTの自動retry/fallbackは0。

生成POSTの総上限と管理呼出しの上限は別にする。限定確認の管理枠案はjobあたりstatus 20秒以上間隔/監視60分で最大180回、result回収は既存上限の最大3試行、cancel 1回、ACL GET 2回、token発行3回、匿名GET 2回、追加Bearer診断GET 3回。自然期限観測用tokenは期限観測直前に発行する。これらもD1で単調予約し、再読込/再起動で補充しない。初回の回収用tokenが3試行で枠を使い切った場合は期限診断をunknownとし、追加発行で続けない。終了後の上流照合は同じIDへのstatus追加最大3回と削除最大3試行を別枠にし、停止時刻＋24時間で専用経路を閉じる。上流admin削除を本人の別手段で行う場合も同じ試行上限と対象を実行票へ含める。未完/unknownは期限後も台帳に残し、追加照合は別承認。management枠は新規生成枠を増やさず、保持期限やcreated_at＋1時間の回収期限も延長しない。枠の数値は実装時レビュー用の案で、今回設定/照会していない。

再起動/再配備/UTC日付変更/ログインし直しでrun・時刻・総消費を再作成/加算前へ戻さない。migrationはtableだけを追加し、通常起動/HTTPでrunをseedしない。別DB binding/別run ID/設定hash不一致、行の欠落、schema未適用は閉じる。次の窓や新runは別の具体的な承認・登録作業になる。

復元/rollback前には専用送信をOFFにし、正しい復旧witnessへprobe run/slot/消費/停止/削除記録も含めて照合する。復旧後に古い「0回・未停止」へ戻っても、照合なしでは再有効化しない。witnessの実保管先は本人限定の承認済み保管先を実行前に確定し、今回DB exportや新保管先を作らない。既存M-0の本文終端30日/本文なし台帳終端90日・未終端保持を維持する。全関連job終端から90日後に専用最小記録を消去する場合も、承認設定は退役済み/新規送信OFFとし、run欠落を初期化理由にしない。unknownは日数だけで消さない。

### 1回目の判定と2回目の停止

判定は`pass / fail / unknown / not_due`を区別する。not_dueは期限をまだ迎えていない観測項目で、passではない。1つでもfail/unknownなら受付を閉じる。今回は厳格案を採用済みで、2回目は判定にかかわらず送らず、自然期限等を受付停止後に照合する。

| 受付/回収 | 固定queue経路・request IDでstatus/resultを確認し、Store-IO=0のままJSON回収。timeout/不正応答/不明ID保存/別endpoint・別CDN・null metadataで停止。再POSTで要求IDを作り直さない |

### 別承認後の実行順序
